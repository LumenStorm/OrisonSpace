# 任务存储与项目索引开发日志

## 背景

这次开发的目标，是把项目登记、任务入库、任务查询和轻量资产索引这条链路真正落下来，同时保持本地项目文件仍然是创作内容的权威来源。

核心原则有四个：

1. `project_id` 用五位顺序号
2. `task_id` 由服务端生成
3. 数据库只管任务流水和轻量索引，不接管完整创作正文
4. 请求体尽量人话，不把内部编排结构暴露给前端

## 本次完成内容

### 1. 共享契约改造

任务请求体收敛成了现在这组字段：

```json
{
  "projectId": "00001",
  "targetId": "act_1",
  "assetIds": ["char_001", "loc_002"],
  "type": "outline.rewrite",
  "name": "重写第一幕冲突",
  "description": "强化主角和对手第一次正面冲突",
  "input": "让冲突更紧张。"
}
```

同时新增了项目注册契约：

- `projectCreateRequestSchema`
- `projectCreateResponseSchema`

### 2. 项目注册接口

新增：

- `POST /v1/projects`

服务端现在会：

- 根据 `localFingerprint` 查重
- 已存在时返回已有项目
- 不存在时分配下一个五位顺序 `projectId`

这一层的落地，让后续任务接口可以直接依赖服务端项目存在性校验。

### 3. 任务持久化

任务不再只是内存态，而是写入 PostgreSQL：

- `tasks`
- `task_asset_refs`

同时引入了服务端 `taskId` 生成函数，格式固定为：

```text
YYYYMMDDHHmmssSSS_<random5>
```

### 4. 项目任务列表与资产列表

新增：

- `GET /v1/projects/:projectId/tasks`
- `GET /v1/projects/:projectId/assets`

其中任务列表没有走逐条查资产，而是：

1. 先查任务列表
2. 再批量查 `task_asset_refs`
3. 在内存中按 `taskId` 分组补齐 `assetIds`

这样避免了明显的 N+1 查询。

### 5. 轻量资产索引

任务完成后，服务端会根据 `assetIds` upsert `project_assets`。

当前这一层是轻量实现，先写入这些占位信息：

- `assetType = "unknown"`
- `assetName = assetId`
- `assetStatus = "active"`
- `summary = request.description`

它的定位不是资产正文仓库，而是任务与资产之间的轻量索引层。

### 6. 修正资产索引主键设计

这个是实现过程中发现并修掉的关键问题。

最开始 `project_assets` 把 `asset_id` 当成全局主键，会导致不同项目下同名资产互相覆盖。后面已经修正为：

```text
PRIMARY KEY (project_id, asset_id)
```

这让资产索引真正变成“项目内资产索引”，不再串项目。

### 7. 桌面端接入

桌面端这轮做了两层适配：

1. Inspector 里补回真实的任务发起入口
2. 新建 / 打开项目时补服务端项目注册

现在桌面端行为是：

- 新建项目时尝试登记 `projectId`
- 打开项目时如果本地元数据缺少 `projectId`，会尝试补登记
- 提交任务时必须携带已登记的 `projectId`

这比之前直接写死 `00001` 或依赖旧任务结构要稳很多。

## 结论

这次改动把“项目登记 + 任务入库 + 任务查询 + 资产轻量索引 + 桌面端联动”这条线真正接起来了。

它最关键的价值，不只是多了几个接口，而是把边界定住了：

- 本地项目文件负责创作正文
- 服务端负责任务流水和索引
- 桌面端不再自己伪造任务主键
- 不同项目之间的资产索引不会再互相覆盖

后面无论继续补分页、补真实资产类型，还是把任务详情做厚，都会比之前顺手很多。
