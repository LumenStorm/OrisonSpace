# Orison Space 用户痛点与产品模块规划

> **For agentic workers:** 本文是产品规划文档，不是直接实现计划。任何具体开发前，需要拆分为独立 spec / plan，并与 `2026-06-30-long-term-cba-roadmap.md` 的 C -> B -> A 顺序对齐。

**Goal:** 梳理 Orison Space 面向长篇创作者时最急需解决的用户痛点、长期痛点、完整产品所需模块，以及当前设置中心和系统配置能力的缺口。

**Context:** 当前项目已经具备本地项目、章节编辑、AI 生成、图像生成、Agent、时间线、模型配置等基础，但距离完整产品还缺少清晰的新手路径、可信赖的保存/恢复体系、成熟设置中心、方法论入口和模块化产品体验。

**Product Principle:** 功能模块不应只按技术能力堆叠，而应围绕用户问题组织：用户为什么来、卡在哪里、怕什么、完成作品前还缺什么。

---

## Pain Priority

### P0: 用户不知道如何开始

**Problem:** 用户打开创作工具后，经常面对空白项目，不知道先写大纲、角色、第一章，还是先配置模型。AI 工具越多，入口越容易让人困惑。

**Product Response:**

- 新建项目向导。
- 示例项目。
- “下一步建议”面板。
- 首章生成/章节目标引导。
- 创作方法论文档入口。

**Acceptance Criteria:**

- 新用户 10 分钟内可以创建项目并生成或写出第一段有效内容。
- 新项目不再只是空白编辑器，而有明确的第一步。

### P0: 用户害怕丢稿和不可恢复

**Problem:** 写作者最怕保存失败、误覆盖、AI 改坏、应用崩溃、更新后项目打不开。对创作工具来说，可信赖比炫酷更重要。

**Product Response:**

- 自动保存状态明确。
- 版本快照/时间线可理解。
- 关闭前未保存守卫。
- 备份目录和恢复入口。
- 修改前 diff 和接受/拒绝。
- 项目健康检查。

**Acceptance Criteria:**

- 用户随时知道当前内容是否已保存。
- AI 修改不会静默覆盖用户作品。
- 用户能恢复最近版本或导出备份包。

### P0: AI 不可控

**Problem:** 很多 AI 写作产品的问题不是“不能生成”，而是“生成后用户不知道改了什么、为什么改、怎么撤回”。长篇创作尤其需要可控、可审阅、可回滚。

**Product Response:**

- Agent 修改必须以 diff / patch 呈现。
- 高风险工具调用必须确认。
- 每次 AI 输出带理由和影响范围。
- 支持拒绝、部分接受、撤回。
- Agent 执行过程可见。

**Acceptance Criteria:**

- 用户能在接受前看懂 AI 修改。
- 用户能拒绝不满意的 AI 输出，而不破坏当前稿件。

### P1: 长篇一致性崩坏

**Problem:** 长篇项目会出现人物设定漂移、世界观冲突、伏笔丢失、章节节奏松散、前后文矛盾。这是普通聊天式 AI 很难解决的长期痛点。

**Product Response:**

- 角色卡、地点卡、组织卡、道具卡。
- 世界观规则和禁忌。
- 伏笔表和回收状态。
- 章节摘要和长期记忆。
- 一致性检查 skill。
- 章节审稿中心。

**Acceptance Criteria:**

- 用户能定位某个角色/设定在哪些章节出现。
- 审稿工具能指出明显一致性风险。

### P1: 配图不是单点生图

**Problem:** 小说配图真正需要的是一致的视觉资产体系，而不只是随机生成一张图。角色外观、场景氛围、封面风格、章节插图需要共享设定和风格。

**Product Response:**

- 图像 brief 生成。
- 角色/场景/封面风格模板。
- 图片与角色、地点、章节、封面用途关联。
- 素材库元数据。
- prompt、模型、参数记录。
- 图片编辑和入库确认。

**Acceptance Criteria:**

- 用户知道一张图来自哪个角色/场景/章节。
- 同一角色可以复用外观描述和风格约束。

### P1: 模型配置对作者太技术化

**Problem:** BYO API Key 对开发者友好，但对普通作者有门槛。baseUrl、modelId、capability、失败错误等概念需要产品化解释。

**Product Response:**

- 模型连接测试。
- 文本/图像/视频/Agent 用途分配。
- 推荐配置模板。
- 错误原因翻译。
- 模型能力自动识别和手动修正。
- 费用和上下文长度提示。

**Acceptance Criteria:**

- 用户可以知道模型是否可用，以及不可用时该怎么修。
- 用户可以给不同场景选择默认模型。

### P2: 最终交付缺失

**Problem:** 用户完成章节后，需要发给编辑、朋友、社群或投稿平台。没有导出、排版和作品包，创作闭环就停在应用内部。

**Product Response:**

- DOCX 导出。
- PDF 导出。
- EPUB / HTML 预览包评估。
- 排版模板。
- 封面和插图位置。
- 作品导出包。

**Acceptance Criteria:**

- 用户可以导出一份能阅读、审阅或投稿的文件。
- 导出格式不乱码，章节顺序和标题层级正确。

## Long-Term Pain Points

### 1. 方法论无法沉淀

用户不是只缺一个按钮，而是缺稳定创作流程。Orison Space 应把“开篇钩子、章节节奏、人物弧光、伏笔回收、爽点节奏、审稿标准”沉淀为文档、模板、skills 和 workflows。

### 2. 资料和正文割裂

如果角色卡、章节正文、图片素材、AI 建议、版本节点互相没有引用，项目会重新散成多个孤岛。需要实体引用、关系图、提及追踪、章节关联和素材绑定。

### 3. 创作上下文越来越重

长篇越写越长，AI 上下文选择会越来越难。需要摘要、记忆、检索、上下文构建策略和用户可控的引用范围。

### 4. 社区贡献容易碎片化

社区如果只贡献 prompt，会很快变成散乱文本。需要统一 skill 结构、方法论模板、示例项目规范和 review checklist。

### 5. 本地优先和易用性之间的张力

本地优先有隐私优势，但配置、备份、模型连接、跨设备迁移都更难。产品需要用设置中心和导出/备份机制补足易用性。

## Product Modules

### 1. Onboarding Center

**Purpose:** 解决“不知道怎么开始”。

**Capabilities:**

- 新建项目向导。
- 体裁/篇幅/目标读者选择。
- 一句话梗概、主角、冲突、第一章目标输入。
- 推荐下一步。
- 示例项目入口。
- 方法论入口。

### 2. Project Home / Dashboard

**Purpose:** 让用户回到项目时知道当前状态。

**Capabilities:**

- 当前写作进度。
- 最近编辑章节。
- 未处理 AI 建议。
- 未完成任务。
- 最近版本节点。
- 下一步建议。
- 项目健康提示。

### 3. Creative Asset Center

**Purpose:** 管理长篇创作资产。

**Capabilities:**

- 角色卡。
- 地点卡。
- 组织/势力。
- 道具/能力/规则。
- 伏笔表。
- 时间线。
- 关系图。
- 标签和提及追踪。

### 4. Review Center

**Purpose:** 把 AI 从生成器变成审稿伙伴。

**Capabilities:**

- 章节节奏审稿。
- 人物一致性检查。
- 世界观冲突检查。
- 伏笔回收检查。
- 重复表达和语气检查。
- 审稿报告。
- 可接受 patch。

### 5. Visual Asset Center

**Purpose:** 让配图围绕小说资产工作。

**Capabilities:**

- 角色图。
- 场景图。
- 道具图。
- 封面 brief。
- 章节插图 brief。
- 风格模板。
- 素材库。
- 图片与项目实体关联。

### 6. Agent Workbench

**Purpose:** 提供可控自动化。

**Capabilities:**

- Agent 会话。
- Tool 调用过程。
- 确认卡片。
- Diff 审阅。
- 子代理过程树。
- Abort / retry / restore。
- Agent 权限管理。
- 运行日志。

### 7. Skills Library

**Purpose:** 支撑社区方法论复用。

**Capabilities:**

- 内置 skills。
- 社区 skills。
- 按包启用/禁用。
- Skill 权限。
- Skill 版本。
- Skill 输入输出说明。
- Skill 执行报告。

### 8. Export Center

**Purpose:** 让作品离开应用也成立。

**Capabilities:**

- DOCX 导出。
- PDF 导出。
- EPUB / HTML 评估。
- 排版模板。
- 封面/插图插入。
- 导出预览。
- 导出包。

### 9. Backup & Recovery Center

**Purpose:** 建立写作者信任。

**Capabilities:**

- 自动保存策略。
- 快照频率。
- 备份目录。
- 恢复入口。
- 项目健康检查。
- 数据迁移。
- 打开数据目录。

### 10. Community & Methodology Hub

**Purpose:** 把产品变成创作系统和社区入口。

**Capabilities:**

- 方法论文档。
- 教程。
- 示例项目。
- 模板。
- Skill 贡献指南。
- Roadmap。
- 社区讨论入口。

当前设置页偏少，导致产品系统感不足。未来设置中心应从“配置模型和外观”扩展为“管理整个创作系统”。

- 语言。

- 默认项目目录。

- 行宽。
- 行距。

- 缩放。

### Models

- Agent 默认模型。
- 上下文长度提示。
- 错误诊断。

- 高风险操作确认策略。

### Skills

- 来源目录。

### Writing

### Images

### Export

- 页眉页脚。

- 重建索引。
- 开发者诊断。
- IPC / Agent 调试开关。

## Product Completeness Gap

### 当前已有基础

- 本地项目结构。
- 章节和创作字段编辑。
- 模型配置和 OpenAI-compatible 调用。
- 图像生成和本地编辑基础。
- Agent runtime 和 skill 基础。
- 时间线和版本管理基础。
- IPC 安全边界和 path guard。
- 三平台 CI/release 基础。

### 距离完整产品还缺

- 清晰新手路径。
- 可信保存、备份、恢复体验。
- 完整设置中心。
- 用户可理解的 Agent 工作台。
- 方法论和示例项目。
- Skill 生态规范。
- 长篇一致性检查。
- 配图资产体系。
- DOCX/PDF/EPUB 导出。
- 发布和安装信任。
- 社区贡献路径。

### 判断标准

一个更完整的 Orison Space 应满足：

- 用户第一次打开不会迷路。
- 用户写作时不怕丢稿。
- 用户能控制 AI，而不是被 AI 覆盖。
- 用户能长期维护人物、世界观、伏笔和章节。
- 用户能把作品导出给别人看。
- 用户能安装、更新、备份、迁移。
- 社区能贡献方法、skill、模板和示例项目。

## Suggested Priority

### First: Trust and Onboarding

- 修文档乱码。
- 补 README 截图。
- 做新手项目向导。
- 做示例项目。
- 强化保存/恢复说明。

### Second: Settings Center

- 扩展设置中心信息架构。
- 先补 Models、Backup、Agent、Skills、Export 的骨架。
- 不必一次性实现所有设置，但要让用户看到系统边界。

### Third: Review and Consistency

- 做章节审稿。
- 做人物一致性检查。
- 做伏笔检查。
- 将这些变成 starter skills。

### Fourth: Visual and Export

- 做图像 brief 和素材关联。
- 做 DOCX baseline。
- 做 PDF baseline。
- 再考虑 EPUB。

## Open Questions

- 设置中心优先做“真实可用配置”，还是先做完整信息架构骨架？
- 新手引导是否应该成为项目首页的一部分，还是单独 wizard？
- 备份恢复是先做项目目录内快照，还是 `~/.orison` 统一管理？
- 配图资产要不要优先支持本地 ComfyUI / Stable Diffusion 工作流？
- DOCX/PDF 导出优先满足投稿格式，还是优先满足阅读体验？
- 社区 skill 是先放在仓库内，还是预留外部 skill registry？

---

## Non-Goals

- 不把设置中心变成复杂后台管理系统。
- 不在短期内做云同步和账号体系。
- 不用“更多按钮”替代清晰用户路径。
- 不让 AI 自动覆盖用户稿件。
- 不把配图做成和小说项目无关的普通图库。
