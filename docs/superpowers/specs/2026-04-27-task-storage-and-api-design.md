# Task Storage and API Design

## Goal

Define a task and asset-index persistence model that keeps project source content local-first, while making task creation, task tracking, and asset lookup easy to query on the server side.

This design has four core goals:

1. Keep request payloads simple and readable.
2. Store only task flow and asset index data in PostgreSQL.
3. Keep long-form project content and detailed creative artifacts in local plaintext project files.
4. Shape the server so later read/write splitting and list-query performance work without re-architecting.

## Scope

This design covers:

1. `project_id` and `task_id` rules.
2. Task creation request and response shape.
3. Which fields go to PostgreSQL and which stay local.
4. Task, project, and asset index table design.
5. Read/write repository boundaries.
6. Query patterns that avoid N+1 behavior.
7. Validation and error-handling expectations.

This design does not cover:

1. Full cloud project storage.
2. Migration of complete local project documents into the database.
3. Final orchestration execution internals.
4. Frontend UI redesign.

## Core Decisions

### 1. `project_id` is sequential

`project_id` is a five-character, zero-padded sequential identifier:

- `00001`
- `00002`
- `00003`

It is created once per project and remains stable for the lifetime of the project.

This identifier exists to make project grouping, debugging, logs, and manual DB inspection easy.

### 2. `task_id` is timestamp plus five random digits

`task_id` is generated by the server, not the client.

Format:

```text
YYYYMMDDHHmmssSSS_<random5>
```

Examples:

- `20260427214530123_48321`
- `20260427214530988_10452`

This keeps IDs human-readable, mostly time-ordered, and safe to generate without asking the client to coordinate uniqueness.

### 3. The request body stays product-shaped

The client should not send internal orchestration structure such as nested scope descriptors, internal patch metadata, or verbose asset objects.

The request body should express:

- which project this belongs to
- which target entity this acts on
- which related assets are relevant
- what the task is called
- what the task is trying to do
- what input text should be fed into processing

### 4. The database stores task flow and asset indexes only

PostgreSQL stores:

- project metadata
- task metadata and status flow
- task-to-asset references
- light asset index records

PostgreSQL does not store:

- full local project documents
- large creative field payloads
- full asset card documents
- full relationship graph documents
- long prompt bodies and raw creative artifacts as the system of record

## API Design

### Create Task

`POST /v1/tasks`

Request:

```json
{
  "projectId": "00001",
  "targetId": "act_1",
  "assetIds": ["char_001", "loc_002"],
  "type": "outline.rewrite",
  "name": "Rewrite first act conflict",
  "description": "Strengthen the first direct conflict between protagonist and rival",
  "input": "This is the text content submitted with the task"
}
```

Rules:

1. `projectId` is required.
2. `targetId` is optional, because some tasks operate on a whole project rather than one entity.
3. `assetIds` is optional and contains only identifiers, never full asset objects.
4. `type` is required and expresses the task family.
5. `name` is a short human-readable label for lists and history.
6. `description` is a concise business intent summary.
7. `input` is the main text payload that should be processed.

Response:

```json
{
  "taskId": "20260427214530123_48321",
  "projectId": "00001",
  "status": "queued"
}
```

### Get Task Detail

`GET /v1/tasks/:taskId`

Returns:

- task metadata
- current status
- summary and error state
- related asset IDs

It may include lightweight output metadata, but should not become the source of truth for full creative content.

### List Project Tasks

`GET /v1/projects/:projectId/tasks`

Purpose:

- task timeline
- task history
- status filtering
- list views

### List Project Assets

`GET /v1/projects/:projectId/assets`

Purpose:

- light asset lookup
- asset list panels
- reverse lookup from task history to asset index

## Database Design

### `projects`

Columns:

- `project_id` `varchar(5)` primary key
- `project_name` `varchar(255)` not null
- `project_type` `varchar(32)` not null
- `local_fingerprint` `varchar(255)` not null
- `created_at` `timestamptz` not null
- `updated_at` `timestamptz` not null

Use:

- project existence validation
- stable grouping key for tasks and assets

### `tasks`

Columns:

- `task_id` `varchar(32)` primary key
- `project_id` `varchar(5)` not null
- `target_id` `varchar(128)` null
- `task_type` `varchar(64)` not null
- `name` `varchar(255)` not null
- `description` `text` not null
- `input_text` `text` not null
- `status` `varchar(32)` not null
- `result_summary` `text` null
- `error_message` `text` null
- `created_at` `timestamptz` not null
- `started_at` `timestamptz` null
- `finished_at` `timestamptz` null
- `updated_at` `timestamptz` not null

Indexes:

- index on `project_id, created_at desc`
- index on `project_id, status, created_at desc`
- index on `project_id, target_id, created_at desc`

### `task_asset_refs`

Columns:

- `task_id` `varchar(32)` not null
- `asset_id` `varchar(128)` not null

Primary key:

- `(task_id, asset_id)`

Indexes:

- index on `asset_id`

Use:

- reverse lookup
- task detail hydration
- asset usage listing

### `project_assets`

Columns:

- `asset_id` `varchar(128)` primary key
- `project_id` `varchar(5)` not null
- `asset_type` `varchar(32)` not null
- `asset_name` `varchar(255)` not null
- `asset_status` `varchar(32)` not null
- `source_task_id` `varchar(32)` null
- `summary` `text` null
- `version` `integer` not null default `1`
- `updated_at` `timestamptz` not null

Indexes:

- index on `project_id, asset_type, updated_at desc`
- index on `project_id, asset_name`

Use:

- light asset browsing
- asset lookup by project
- source task traceability

## Storage Boundary

### Store in PostgreSQL

Store these fields in PostgreSQL:

1. Project metadata:
   - `project_id`
   - `project_name`
   - `project_type`
   - `local_fingerprint`

2. Task flow data:
   - `task_id`
   - `project_id`
   - `target_id`
   - `task_type`
   - `name`
   - `description`
   - `input_text`
   - `status`
   - `result_summary`
   - `error_message`
   - timestamps

3. Asset index data:
   - `asset_id`
   - `asset_type`
   - `asset_name`
   - `asset_status`
   - `source_task_id`
   - `summary`
   - `version`

4. Lightweight relations:
   - task-to-asset references

### Keep local plaintext as source of truth

Keep these local and plaintext:

1. Full project documents:
   - `outline`
   - `outline_v2`
   - `detailed_outline`
   - `novel`
   - `script`
   - `storyboard`
   - `video`

2. Creative field documents:
   - `creative_brief`
   - `world_setting`
   - `episode_outlines`
   - `growth_curve`
   - `pacing_curve`
   - `emotion_curve`
   - `foreshadow_registry`

3. Detailed asset content:
   - full `asset_cards`
   - full `relationship_graph`

4. Long-form processing payloads:
   - raw prompt bodies
   - large context payloads
   - long AI output text

## Read/Write Split Design

Even if the first version still points both repositories at the same PostgreSQL instance, the code should separate read and write paths now.

Recommended repository boundaries:

- `projectWriteRepository`
- `projectReadRepository`
- `taskWriteRepository`
- `taskReadRepository`
- `assetWriteRepository`
- `assetReadRepository`

Write path responsibilities:

- create project
- allocate next sequential `project_id`
- create task
- update task status
- insert task asset references
- upsert asset index records

Read path responsibilities:

- task detail
- task list
- asset list
- lightweight asset detail

This keeps future read-replica adoption from leaking into service-layer logic.

## Query Strategy and N+1 Avoidance

The service must not fetch related records one row at a time in loops.

### Task list hydration

For a task list:

1. Query tasks in one paged query.
2. Collect the returned `task_id` values.
3. Query `task_asset_refs` once with `where task_id in (...)`.
4. Group the asset references in memory.
5. Return hydrated list items.

Do not:

1. query tasks
2. then query refs once per task

### Task detail hydration

For task detail:

- use a single join query or
- use one task query plus one batched related-ref query

### Asset listing

For project asset lists:

- query `project_assets` directly by `project_id`
- paginate and filter at the database level

### Pagination

Task and asset list APIs should default to pagination. No endpoint should load unbounded task history by default.

## Validation and Error Handling

### Validation

Reject requests when:

1. `projectId` is missing or malformed.
2. `type` is missing.
3. `name` is blank.
4. `description` is blank.
5. `input` is blank.
6. `assetIds` contains invalid values.

### Error cases

- `404` when `projectId` does not exist
- `400` when request validation fails
- `409` when a sequential `project_id` allocation collides and retry fails
- `500` when persistence fails unexpectedly

If `task_id` generation collides, the server should retry with a fresh random five-digit suffix before surfacing failure.

## Testing Strategy

Minimum required tests:

1. Creating a task generates a server-side `task_id`.
2. Generated `task_id` matches `timestamp + five random digits`.
3. Creating projects allocates zero-padded sequential `project_id` values.
4. Task creation persists `assetIds` into `task_asset_refs`.
5. Project task list returns related asset IDs without per-row query behavior.
6. Asset index upsert updates `version` and `updated_at`.
7. Invalid request bodies fail schema validation clearly.

## Recommended First Implementation Slice

Implement in this order:

1. Shared contract update for the simplified task request shape.
2. Server-side `task_id` generation.
3. Sequential `project_id` generation.
4. PostgreSQL schema for `projects`, `tasks`, `task_asset_refs`, and `project_assets`.
5. Read/write repository interfaces and first PostgreSQL implementation.
6. Task create and task read endpoints.
7. Project task list and asset list endpoints.
8. Focused tests for ID generation, persistence, and list hydration.
